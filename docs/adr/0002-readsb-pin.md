# ADR-0002: readsb pin — wiedehopf v3.16.16 d9a4c62, plain build

## Status

Accepted (spec §31 ADR #2; plan A0 task).

## Context

readsb-hub performs Mode-S decode, CPR resolution, and dedup — reused, never
reimplemented (AI-10). Spec §12.5 requires golden fixtures for every consumed
field of the *pinned* build and a shadow-replay gate on any upgrade; readsb
data formats change between versions (spec §33 note 3). Plan A0: "Pin the
readsb build (ADR 2): verify `WITH_UUIDS`, capture golden JSON fixtures,
measure `source_timestamp_quantization_ms` (§10.4)."

## Decision

Pin **wiedehopf/readsb v3.16.16, commit `d9a4c62`**
(`d9a4c62655490e70d07704e207738bb9c6cffde1`, committed 2026-08-17), vendored
at `vendor/readsb/`, built by `deploy/build-readsb.sh`:

```
make -j"$(nproc)" OPTIMIZE="-O2"
```

- All SDR backends stay off (Makefile defaults: RTLSDR/BLADERF/HACKRF/
  PLUTOSDR/SOAPYSDR all `no`); there is no separate network-only target — a
  plain `make` already produces a hub binary with zero SDR libs.
- Binary self-reports: `readsb version: 3.16.16 wiedehopf git: d9a4c62`.

**`WITH_UUIDS` verified and declined.** Per `docs/requirements/code-readsb.md`
(Makefile:17-19, api.c:601-610): the flag stores the last 32 receiver ids per
aircraft and enables only the re-api `&filter_uuid=` filter. Receiver ids
arrive from `beast_reduce_plus`/`--net-receiver-id` ingest or `uuid=` connector
elements — a single anonymous ADSBHub `sbs_in` upstream carries no receiver
identity, so the flag buys nothing and costs memory. adsb.lol builds a
separate `readsb-with-uuids` binary for its multi-feeder ingest/api tier;
that pattern does not apply here. Plain build (`WITH_UUIDS` unset = `no`).

Build deps (Ubuntu 24.04, verified): `build-essential`, `pkg-config`,
`libncurses-dev`, `zlib1g-dev`, `libzstd-dev`. Runtime linkage (ldd): libm,
libzstd, libz, libncurses, libtinfo, libc only.

**Upgrade gate** (spec §12.5): any readsb change requires golden fixtures to
pass **and** a ≥30-minute shadow replay; the upgrade is blocked on
incompatible field mapping, parse-error increase, or freshness regression.
Procedure and rollback: `runbooks/readsb-upgrade-rollback.md` (retain the
previous build per §20.6).

Golden fixtures live in `test/fixtures/sbs/` (per-MSG-subtype inputs) and
`test/fixtures/api/` (recorded jv2 envelope); the pin record — build facts,
timestamp-handling semantics, and the measured
`source_timestamp_quantization_ms` — is `docs/readsb-pin.md`.

## Consequences

- Upgrades are deliberate, gated events, never routine package bumps
  (plan §4 "readsb upstream drift" risk).
- Fixtures are pinned to *actual* d9a4c62 behavior, quirks included (e.g. the
  field-20 emergency else-branch reading t[21], net_io.c:3280-3286) — do not
  "fix" expectations against upstream bugs.
- The invocation contract (which flags are safe / forbidden) is DESIGN.md §3;
  args are generated by `deploy/gen-readsb-args.py` and verified by
  `test/unit/test_deploy_args.py` (generated vector = DESIGN.md §3 set;
  `--systemd` output = the frozen unit ExecStart line) plus install.sh's
  §18.3 gate, which re-checks the unit line against the generator over the
  installed `/etc/retina-adsb/readsb.yaml` and refuses on mismatch.
- GPL-3 source stays vendored intact with `COPYING` (see `docs/licenses.md`,
  `vendor/VENDOR.md`).
